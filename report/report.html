1. Problem, dataset and solution overview

Problem. Predict whether a patient has heart disease from routine clinical measurements, and serve that prediction through a monitored REST API that is ready for the cloud.

Dataset. UCI Machine Learning Repository, Heart Disease, file processed.cleveland.data. It has 303 rows, 13 input features and the label num (0 = no disease, 1–4 = increasing severity). Following the usual convention, num > 0 is mapped to the binary target 1.

FeatureDescriptionType
ageAge in yearsnumeric
sex1 = male, 0 = femalebinary
cpChest pain type (1 typical angina, 2 atypical, 3 non-anginal, 4 asymptomatic)nominal
trestbpsResting blood pressure (mmHg)numeric
cholSerum cholesterol (mg/dl)numeric
fbsFasting blood sugar > 120 mg/dlbinary
restecgResting ECG result (0–2)nominal
thalachMaximum heart rate achievednumeric
exangExercise-induced anginabinary
oldpeakST depression induced by exercisenumeric
slopeSlope of the peak exercise ST segment (1–3)nominal
caNumber of major vessels coloured by fluoroscopy (0–3)numeric (count)
thal3 normal, 6 fixed defect, 7 reversible defectnominal

Solution at a glance

  • Data: src/data.py downloads, de-duplicates and imputes the data, then writes data/processed/heart_clean.csv.
  • Modelling: a single scikit-learn Pipeline (preprocessing + classifier). Logistic Regression and Random Forest are tuned with GridSearchCV and 5-fold stratified cross-validation.
  • Tracking: MLflow records the parameters, CV and test metrics, ROC and confusion-matrix plots, and the model for every run.
  • Quality gates: flake8 and 14 pytest unit tests run in GitHub Actions (mirrored locally by scripts/ci_local.sh). Any failure stops the pipeline.
  • Serving: FastAPI /predict in a slim Python 3.11 image, run with Docker Compose and on Kubernetes (raw manifest and Helm chart).
  • Observability: JSON request logs, Prometheus metrics, and a pre-provisioned Grafana dashboard.

3. Data acquisition and exploratory data analysis

Acquisition and cleaning (src/data.py)

  • The file is downloaded from the UCI archive with requests and cached in data/raw/. The step is idempotent.
  • ? is parsed as missing. Only ca (4 rows) and thal (2 rows) have gaps. Both are discrete codes, so they are filled with the mode.
  • Duplicates are dropped, types are coerced to integers, and num becomes the binary target.
  • Result: 303 rows with no missing values. 164 no disease / 139 disease (46% positive).

Fig 1. Class balance: close to even, so no resampling is needed

Fig 2. Correlation heatmap

Fig 3. Numeric feature distributions by target (0 = no disease, 1 = disease)

Key findings

  • Strongest correlations with the target: thal 0.52, ca 0.46, exang 0.43, oldpeak 0.42, thalach −0.42, cp 0.41.
  • Patients with disease reach a lower maximum heart rate (mean 139 vs 158 bpm), show more ST depression (1.6 vs 0.6) and are slightly older (56.6 vs 52.6 years).
  • Cholesterol (0.09) and fasting blood sugar (0.03) carry little signal on their own.
  • cp, thal, restecg and slope are nominal codes, so they are one-hot encoded rather than treated as ordered numbers.

4. Feature engineering and model development

Preprocessing (src/features.py)

GroupColumnsSteps
Numericage, trestbps, chol, thalach, oldpeak, caSimpleImputer(median) → StandardScaler
Categoricalsex, cp, fbs, restecg, exang, slope, thalSimpleImputer(most_frequent) → OneHotEncoder(handle_unknown="ignore")

This gives 25 engineered features. The ColumnTransformer sits inside the same Pipeline as the classifier, so it is fitted only on training folds (no leakage) and the identical transform runs at serving time.

Model selection and tuning (src/train.py)

  • Stratified 80/20 train/test split (seed 42). Tuning uses only the training set.
  • GridSearchCV with 5-fold StratifiedKFold, optimising ROC-AUC.
  • Logistic Regression: C ∈ {0.01, 0.1, 1, 10}, L2 penalty. Best C = 0.1 (strong regularisation suits n = 242).
  • Random Forest: n_estimators ∈ {100, 300}, max_depth ∈ {None, 4, 8}, min_samples_leaf ∈ {1, 3}. Best: 100 trees, unlimited depth, min_samples_leaf = 3.
  • The best model is chosen by cross-validated ROC-AUC, not by the small 61-row test set.

Why Logistic Regression. It scores higher on every cross-validated metric. Its coefficients are directly interpretable, which matters in a clinical setting. It is also tiny and fast to serve. On only 303 rows, the Random Forest's extra capacity adds variance without improving accuracy. Test recall of 0.93 means 26 of 28 disease cases are caught, which is the priority for a screening tool.

5. Experiment tracking

MLflow (file store ./mlruns, experiment heart-disease) logs one run per candidate model for each training execution:

  • Parameters: model type and the best hyperparameters from the grid search.
  • Metrics: 5 CV metrics (accuracy, precision, recall, F1, ROC-AUC) and the same 5 on the test set.
  • Artifacts: ROC curve and confusion matrix PNGs, plus the full sklearn pipeline as an MLflow model with an input example.

Training ran three times (CLI, notebook, local CI) with identical results, which confirms reproducibility with fixed seeds.

6. Model packaging and reproducibility

  • Format: the fitted Pipeline (preprocessing + model) is saved to models/model.joblib. The same pipeline is also logged as an MLflow model, with MLmodel, conda.yaml and requirements.txt generated by MLflow.
  • Metadata: models/metrics.json stores the selected model, the best parameters, the run IDs and all metrics.
  • Environment: every dependency is pinned in requirements.txt (training) and requirements-api.txt (serving).
  • Determinism: one RANDOM_STATE = 42 covers the split, the CV folds and the models. The column lists and paths are defined once in src/config.py.
  • Same code path: the API calls src.predict.predict(), the same function the notebooks and CLI use, so training/serving skew is impossible by construction.

Unit tests (tests/, 14 tests)

FileWhat is verified

test_model.pypreprocessor output shape and no NaNs, unseen category handled, predict output contract, end-to-end train() with MLflow into a temp dir

GitHub Actions (.github/workflows/ci.yml)

Triggered on push to main, on pull requests, and manually. Job lint-test-train: checkout → Python 3.11 with pip cache → install → flake8 → pytest (JUnit XML) → download data → EDA → train. It uploads test-results.xml, train.log, models/, the figures and mlruns/ as workflow artifacts, even on failure. Job docker (needs the first job): builds the image from the trained model, runs it, and smoke-tests /health and /predict, failing if the response lacks confidence. Container logs are always printed.

scripts/ci_local.sh runs the same steps locally with set -euo pipefail.

8. Containerization and API

  • Image: python:3.11-slim, runtime dependencies only, non-root appuser, Docker HEALTHCHECK on /health, model baked in at /app/models/model.joblib.
  • Endpoints: POST /predict (JSON in; prediction, label, probability and confidence out), GET /health, GET /metrics (Prometheus), /docs (Swagger).
  • Validation: a Pydantic schema with range checks on every field. Bad input gets 422 with a clear message.
  • Each response carries an x-request-id header for tracing.

Both use readiness and liveness probes on /health, CPU and memory requests and limits, and prometheus.io/scrape annotations. The Helm chart passes helm lint. Moving to a cloud cluster (GKE/EKS/AKS) only means pushing the image to a registry and changing image.repository.

10. Monitoring and logging

  • Logging: an HTTP middleware writes one JSON line per request (request_id, method, path, status, latency_ms). Each prediction also logs its input and output. The logs go to stdout, so docker logs or kubectl logs collect them.
  • Metrics: api_requests_total{method,endpoint,status}, the histogram api_request_latency_seconds{endpoint}, and model_predictions_total{label} (watches for drift in the class mix).
  • Prometheus scrapes api:8000/metrics every 5 s. Grafana is provisioned automatically with the data source and the "Heart Disease API" dashboard.

Limitations and next steps
